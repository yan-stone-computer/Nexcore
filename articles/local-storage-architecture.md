# 本地智能体怎样存数据：SQLite、工作区与可恢复状态

> 一句话结论：应用状态和项目文件必须分层保存。设置、会话、用量和加密密钥进入本地数据库；附件、产物和项目记忆留在用户选择的工作区。

“本地优先”不能只等于把数据库文件放在电脑上。真实系统里同时存在配置、凭据、会话、附件、生成产物、项目记忆和运行回执，它们的变化频率、生命周期和备份需求并不相同。

NexcoreWork 把存储拆成两个边界清楚的区域：应用状态库与用户工作区。

![NexcoreWork 本地存储架构图](assets/architecture/storage.svg)

## 1. SQLite 保存应用自己的状态

SQLite 负责那些属于应用、但不属于某个具体项目的状态：

- 模型服务商与端点配置；
- API Key 的加密结果；
- 会话索引和窗口设置；
- 工具、模型和语音用量；
- 价格表与统计设置；
- 界面偏好和运行护栏；
- 最近任务与恢复入口。

这些数据需要事务、查询和版本升级，但不适合散落成大量小文件。

## 2. 密钥不能作为普通设置明文保存

API Key 属于高敏感数据。即便数据库只存在于本机，也应该：

1. 使用带随机盐的迭代式密钥派生；
2. 使用认证加密保存密文；
3. 主密钥与应用数据分域保存；
4. 导出备份时默认排除密钥；
5. 日志和错误信息不输出完整 Key。

“只存本地”不是不加密的理由。电脑丢失、目录被同步或误发备份时，明文密钥都会直接泄露。

## 3. 工作区保存用户真正拥有的文件

工作区是用户主动选择的项目目录。附件、生成文件、代码、图片和 `.NexcoreWork` 项目记忆都跟随工作区。

这样做的价值是：

- 卸载或升级应用不会删除项目；
- 用户可以直接用资源管理器管理文件；
- 换电脑时可以复制整个项目目录；
- 备份工作区不依赖应用数据库；
- 删除对话不等于误删项目。

应用数据库可以重建，用户工作区不能随便动。这个差别必须在删除确认和备份策略里体现。

## 4. 项目记忆是工作区的一部分

`.NexcoreWork` 保存项目级事实、约束、已确认的决策和续接信息。它不复制整个数据库，也不保存每次工具输出的完整原文。

项目记忆需要可读、可改、可删除。否则用户无法检查智能体到底记住了什么，也无法修正错误长期记忆。

## 5. 关闭应用后要能恢复

重启恢复至少包括：

- 上次使用的模型和免费 Auto 设置；
- 工作区路径与权限模式；
- API Key 是否可用；
- 历史会话是否可打开；
- 未完成任务能否继续；
- 用量和价格统计是否保持。

只在内存里保存设置会造成一个典型错觉：配置页看起来已经完全正确，但重启后又回到默认值。

## 6. 迁移与备份要区分三种场景

| 场景 | 应包含 | 不应默认包含 |
|---|---|---|
| 项目迁移 | 工作区文件、产物、`.NexcoreWork` | 全局 API Key |
| 应用设置备份 | 模型、价格、界面和运行设置 | 未授权的聊天附件 |
| 完整设备迁移 | 数据库加密包与工作区 | 明文凭据 |

把三种场景混成一个大 ZIP，既容易泄露，也不方便恢复。

## 7. 失败与并发也需要边界

本地数据库仍然会遇到并发写入、进程退出、磁盘空间不足和文件被占用。系统应使用事务、写入锁和可恢复的临时文件，避免出现“设置写了一半、工作区文件却已覆盖”的状态。

一个可靠的本地存储层，不是看它用了什么数据库，而是看它能否回答：

1. 数据属于应用还是用户；
2. 哪些数据必须加密；
3. 哪些数据可以重建；
4. 删除和备份会影响什么；
5. 重启后怎样恢复。
