# 从一张用户截图修全局图片裁切：HTML height 属性和 CSS 的暗战

> 一句话结论：用户截图里的“图片显示不全”不一定是素材问题，也不一定只影响首屏。先量真实 DOM，再找共同根因，往往能一次修掉整站同类问题。

用户发来一张首页截图，只说了句：

> 首页这个显示都不全好难看。

截图里，产品演示面板变成一块很高的白色区域，界面左右被裁，文字只剩残缺的中间部分。看起来像是某张图片素材坏了，但页面源码里的原图是标准的 `1600 × 1000`。

## 1. 先复现，不先改 CSS

第一步不是猜 `object-fit`，而是在几个真实宽度下读取 DOM 尺寸：

```text
1440 × 1000
917 × 910
768 × 1024
390 × 844
```

在 917 宽度复现后发现：

- 图片宽度约 834px；
- 图片高度却是 **1023px**；
- 整个 hero 高度超过 **1800px**。

原图比例是 1.6:1，实际却被渲染成接近 0.8:1 的竖向区域。问题不在图片文件。

## 2. 根因：HTML 高度属性和 CSS 宽度同时生效

页面里的截图写成了：

```html
<img src="screen.webp" width="1600" height="1000" alt="...">
```

CSS 只改了宽度：

```css
.stage-frame img {
  width: 100%;
  aspect-ratio: 8 / 5;
  object-fit: cover;
}
```

很多人以为 `width: 100%` 会自动把高度按比例缩放，但 HTML 的 `height="1000"` 仍可能作为表现属性参与布局。结果就是：

```text
宽度跟随容器
高度保留 1000px
aspect-ratio 没有把实际盒高拉回预期
object-fit: cover 再把左右裁掉
```

三个因素叠加后，产生了一个非常高的图片框。用户看到的不是“图片加载失败”，而是图片在错误的容器比例里被强行裁切。

## 3. 最小修复：先让响应式图片真正自适应

全局图片先补一条基础规则：

```css
img {
  display: block;
  max-width: 100%;
  height: auto;
}
```

再让产品截图使用与素材一致的原始比例：

```css
.workbench-visual img {
  width: 100%;
  aspect-ratio: 8 / 5;
  object-fit: contain;
}
```

`height: auto` 解决 HTML 属性造成的固定高度，`aspect-ratio` 负责布局预留，`contain` 保证内容不被裁掉。

修复后，917 宽度下 hero 高度从约 1847px 降到约 592px，图片比例恢复到 0.625，也就是原始的 `1000 / 1600`。

## 4. 为什么只改首屏还不够

继续检查发现，工作台、执行过程、模型路由、知识库、运行洞察等截图都有同样风险。

根因在共享的图片基础规则，不在某一个组件。因此修复必须落在公共层：

- 所有图片默认 `height: auto`；
- 带固定尺寸的 Logo 仍通过更具体的规则覆盖；
- 需要预留空间的截图使用素材本身的宽高比；
- 不使用 `cover` 掩盖比例不匹配，先修容器比例。

这就是“根因修复”和“只修用户截图里的那一块”的区别。

## 5. 另一个隐藏 bug：不可见的导航仍然拦截点击

在同一轮手机检查里还发现：

- 导航收起后视觉上移出屏幕；
- 但它仍占据固定定位层，拦截汉堡按钮点击；
- 桌面和手机都没有横向溢出，不代表交互一定正常。

修复方式是把关闭状态显式设为不可交互：

```css
@media (max-width: 760px) {
  .site-header nav {
    visibility: hidden;
    pointer-events: none;
  }

  .menu-open .site-header nav {
    visibility: visible;
    pointer-events: auto;
  }
}
```

仅靠 `transform` 移出屏幕，不等于元素已经不可操作。

## 6. 验证必须看真实渲染

修复后至少检查：

| 项目 | 结果 |
|---|---|
| 1440px 桌面 | 无横向溢出 |
| 917px 中窄屏 | 图片恢复完整比例 |
| 390px 手机 | 无横向溢出，导航可开合 |
| 图片资源 | 无加载失败 |
| CSS 控制台 | 无页面 JS 错误 |
| 产品截图 | 完整显示，不再二次裁切 |

最终还加了可跳转的作品案例页，让“鹈鹕骑单车”不再只是一张缩略截图，而是可以打开、查看完整动画和原始 SVG 的真实交付物。

## 7. 视觉质检让结果不只靠肉眼

页面修复后，NexcoreWork 使用 DeepSeek 作为主模型，调用内置 `builtin_inspect_image` 对首屏截图做复核。

视觉模型确认：

- 导航、主标题、按钮组、产品演示图和底部数据块都在画面内；
- 没有遮挡、错位或比例失真；
- 文字像素不足的区域被标为低置信度，而不是强行下结论。

这次识图调用约 6 秒成功。它补上的不是“审美评价”，而是画面完整性和几何关系的独立证据。

## 8. 这类问题可以怎样排查

下次遇到“图片显示不全”，按这个顺序做：

1. 看原图的真实宽高；
2. 量 DOM 图片盒子的宽高；
3. 检查 HTML 是否写了固定 `height`；
4. 检查 CSS 是否只改了宽度；
5. 检查 `object-fit` 是否在掩盖比例不一致；
6. 检查所有同类图片是否共用同一规则；
7. 在桌面、中窄屏和手机三档截图验证；
8. 有视觉模型时，把真实渲染结果交给它复核。

用户体验中的“看起来不对”，最后通常能落到一个可测量的盒子尺寸、一个继承的 HTML 属性或一个被忽略的交互层。找到共享根因，比逐个组件打补丁更小，也更可靠。
