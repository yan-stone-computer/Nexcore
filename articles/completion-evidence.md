# Agent 说“完成了”不算完成：怎样把交付变成可验证的证据链

> 一句话结论：Agent 的完成状态不能由模型自己宣布，必须由工具回执、文件变化、渲染结果和检查记录共同证明。

“已经完成”“已经修复”“已经验证”是 Agent 最容易说、也最没有成本的三句话。

在普通聊天里，说错一次只是回答不准确；在能读写文件、运行命令的智能体里，错误宣布完成会让用户停止检查，把一个没有运行过的页面、一个缺失的依赖或一张被裁切的图片当成最终交付。

NexcoreWork 的一条核心规则是：模型负责解释，系统负责留证。

## 1. 一次真实的“看起来做完了”

最初的任务是让 Agent 生成“鹈鹕骑单车”的 SVG 动画。模型返回了文件路径和一段漂亮的说明，界面里也有完成状态，但真正打开页面时会遇到这些问题：

- 车轮和曲柄是否同步，没有抽帧检查；
- 脚是否真的踩在踏板上，没有近景复核；
- 页面有没有完整渲染，没有浏览器截图；
- 终端报错有没有出现，模型没有读取实际输出；
- 文件到底写了多少行，只有模型口头描述。

这类失败不是因为模型不会写 SVG，而是因为“生成文件”和“可交付作品”之间少了验证层。

## 2. 完成状态应该由哪些证据构成

一次可核验的交付至少包含以下几层：

| 证据 | 回答什么问题 | 没有它会怎样 |
|---|---|---|
| 工具回执 | 工具真的执行了吗 | 模型可能只写了调用说明 |
| 文件变化 | 改了哪个文件、增加/删除了多少行 | 用户无法知道改动范围 |
| 代码检查 | 语法、引用和静态结构是否成立 | 页面可能一打开就报错 |
| 浏览器渲染 | 产物在真实浏览器里是否出现 | 只读源码不等于能运行 |
| 图片识别 | 画面是否完整、元素连接是否合理 | 完成可能只是“能打开” |
| 最终路径 | 用户能否点到交付物 | 文件存在但不可发现 |

这些证据不是装饰。每一条都对应一个模型过去可以轻易跳过的现实步骤。

## 3. 写入必须先有回执

工具执行后，系统为结果生成回执，记录工具名、参数摘要、耗时、成功状态和返回值。文件类工具还会额外计算：

- 工作区相对路径；
- 新建、覆盖或追加；
- 新增行数；
- 删除行数；
- 内容摘要。

所以最终答复不是“我创建了一个文件”，而是：

```text
website/index.html  +186 / -0
assets/work/pelican-bike.svg  +254 / -0
```

用户至少能知道两件事：文件确实发生了变化，变化发生在哪个位置。

## 4. 写入之后还需要“看”

对于 HTML、SVG、页面和动画，文件写入成功只说明磁盘上多了一段文本。NexcoreWork 增加了一条两步流程：

```text
builtin_render_preview
        ↓
真实 PNG 截图
        ↓
builtin_inspect_image
        ↓
艺术总监/质检视角的问题清单
        ↓
修改后再渲染
```

`builtin_render_preview` 使用本机 Edge/Chrome 无头模式，把工作区里的 HTML 或 SVG 渲染为 PNG。`builtin_inspect_image` 再把图片交给视觉端点，要求检查构图、裁切、比例、遮挡、连接关系和文字可读性。

这两个工具不能互相替代：

- 只看代码，发现不了最终画面是否被裁切；
- 只生成截图，不交给视觉模型，等于没有读图；
- 只读图，不重新渲染，改完的文件也没有被验证。

## 5. 模型只负责“判断”，系统负责“记账”

运行时的职责划分很重要：

```text
模型：决定下一步调用什么工具
系统：校验参数、执行工具、生成回执、记录文件和事件
模型：读取回执，决定是否继续修
系统：保存最终输出、过程记录与交付路径
```

模型可以误以为自己完成了，但不能绕过工具层改状态。

这也是为什么“同一个工具连续失败三次就熔断”很重要。模型最常见的坏行为不是一次失败后停下，而是换参数反复撞同一个坏工具，直到烧完步骤和预算。熔断把“自我修复”限制在一个可控范围里。

## 6. 审批不是拖延，而是内容绑定

高风险写入和命令执行需要审批。审批卡片绑定当前工具、参数和内容摘要，避免出现“批准的是 A，实际执行成了 B”。

批准之后仍然保留回执，拒绝则完全不产生副作用。系统不会把“用户点过同意”当成“所有后续操作都同意”。

这条机制解决的是另一种隐性假完成：模型先让你批准一次，然后连续执行一串你没有看清的附加操作。

## 7. 最终答复如何写

一个合格的 Agent 完成答复应包含：

1. **结果**：交付了什么；
2. **证据**：工具调用、文件变化、测试或渲染结果；
3. **路径**：可点击的文件和页面地址；
4. **边界**：哪些检查成功，哪些仍未验证；
5. **下一步**：只有存在真实阻塞时才给用户选择。

例如：

```text
已完成官网首屏修复：
- 图片恢复 16:10 原始比例
- 1440 / 917 / 390 宽度无横向溢出
- 浏览器验收无资源失败
- 页面地址：https://...

未完成：当前没有对第三方浏览器插件中的表现做验证。
```

这比“全部完成，请放心使用”有用得多。

## 8. 一条最小验证清单

可以把下面的清单直接用于任何可视化 Agent：

- 工具真的执行了吗？
- 执行参数与用户批准的内容一致吗？
- 文件路径在工作区内吗？
- 文件变化有行数和差异吗？
- 能解析、构建或通过静态检查吗？
- 能在真实浏览器里打开吗？
- 关键尺寸有没有截图证据？
- 画面结论有没有交给视觉模型复核？
- 视觉失败有没有明确标注为未核验？
- 用户拿得到可点击的最终文件吗？

只要其中一项没有证据，就不应该把状态写成“已验证完成”。

Agent 的能力上限，取决于它能调用多少工具；Agent 的可信度，取决于它有多少证据。前者决定能做什么，后者决定用户敢不敢把下一件事交给它。
