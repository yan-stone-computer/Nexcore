# Agent 执行闭包：为什么“一次生成”无法完成真实工作

> 一句话结论：Agent 的能力不只来自模型生成了多少文字，而来自“判断下一步、调用工具、观察结果、记录证据”这一循环能否稳定运行并在正确的位置停下。

普通对话只需要一次模型响应。真实工作却会跨越文件、命令、页面、图片和外部服务，任何一步都可能失败。把完整任务压缩成一次文本生成，最终只能得到一份“看起来像答案”的计划，而不是可核验的交付。

NexcoreWork 把执行拆成一个闭环，而不是一条直线。模型负责判断，系统负责执行和记账，交付门禁负责判断结果是否真的成立。

## 1. 规划器只决定方向，不代替执行

任务进入系统后，规划器先识别目标、工作区和验收条件。它可以把任务拆成步骤，选择可能需要的能力，但不能自己宣称文件已经写入、页面已经打开或测试已经通过。

因此，规划输出必须落到可执行动作上：

1. 读取哪个文件或目录；
2. 调用哪个工具；
3. 使用什么参数；
4. 输出进入哪里；
5. 用什么证据判断这一步成功。

没有动作和验收条件的计划，只是自然语言草稿。

## 2. 每一次工具调用都产生可观察结果

Agent 循环中最重要的节点不是“思考”，而是“观察”。工具调用之后，系统至少需要把以下事实返回给模型：

- 工具名和参数摘要；
- 开始与结束时间；
- 标准输出、错误输出和退出码；
- 文件路径与行级变化；
- 结果是否被截断；
- 失败时是否可以重试。

模型看到真实结果，才可能决定修正参数、换工具或停止。如果只把“调用成功”当成观察结果，模型仍然是在盲飞。

## 3. 错误必须回到循环，而不是被一句“已完成”盖住

最常见的假完成来自两种情况：

- 工具报错，但模型没有读取错误就继续生成；
- 模型连续用不同参数撞同一个坏工具，消耗完步骤预算。

闭环需要把错误重新交给观察节点，并限制无意义重试。例如同一个工具连续失败多次后，应停止重复调用，改为检查路径、依赖或权限，必要时向用户说明真正的阻塞点。

停止不是失败。明确的“命令缺少权限”比伪造的成功结果更接近可靠系统。

## 4. 证据写入与执行同步发生

执行证据不能等任务结束再凭记忆补写。每次工具回执、每个文件变化、每个阶段检查，都应该随着执行进入运行记录。

这样才能支持三种行为：

- 中途失败时知道已经完成了什么；
- 用户要求继续时知道从哪里接上；
- 最终答复能够给出文件路径、行变化和真实运行结果。

证据写入也是项目记忆的输入。系统只需要长期保留目标、决策、完成项和阻塞项，不需要把整段工具日志永久注入上下文。

## 5. 交付门禁独立于模型自评

交付门禁负责回答几个确定性问题：

| 检查项 | 要回答的问题 |
|---|---|
| 文件 | 文件是否真实存在且位于工作区内 |
| 语法 | 代码能否解析，页面能否构建 |
| 运行 | 命令是否成功，退出码是否为 0 |
| 渲染 | 页面或图片能否在真实浏览器中打开 |
| 差异 | 新增、修改与删除了哪些行 |
| 路径 | 用户能否直接找到最终产物 |

模型可以建议“现在可以交付”，但只有门禁证据能决定最终状态。

## 6. 这个闭环不保证模型一定聪明

闭环解决的是工程可信度，不是模型能力本身。它仍然可能遇到：

- 模型选错工具；
- 工具参数不完整；
- 外部服务不可用；
- 任务目标本身存在歧义；
- 自动视觉检查遗漏细节。

区别在于，这些问题会以可观察状态出现，而不是被包装成一句模糊的“全部完成”。

## 7. 最小可运行标准

一个执行型 Agent 至少应该满足：

1. 任务开始前有工作区和验收条件；
2. 工具调用有回执；
3. 失败结果可以回到模型；
4. 文件变化有路径与行数；
5. 中途停止后能恢复；
6. 最终答复带可点击产物；
7. 未验证的部分明确标注。

Agent 真正有价值的不是“能连续生成很多字”，而是把每一轮判断都落到现实世界，再用现实结果修正下一轮。
