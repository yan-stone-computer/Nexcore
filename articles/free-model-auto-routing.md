# 免费模型 Auto 不是随机抽卡：一次请求怎样选模型

> 一句话结论：可靠的模型路由不是把所有免费模型放进下拉框，而是先判断任务，再按能力过滤，最后在满足条件的端点中比较成本、窗口、工具可靠性和真实延迟。

“免费模型 Auto”最容易被误解成一个随机轮换器：只要一个模型挂了，就换下一个。

这种实现很快就会暴露问题。问新闻时可能选中不会搜索的模型，带图时可能选中不能看图的模型，长文件任务可能先发出去再被窗口拒绝，代码任务也可能落到工具调用很弱的小模型上。

NexcoreWork 的 Auto 把选择拆成三个固定阶段，并把结果写入运行轨迹。

## 1. 第一阶段：先看任务

路由不会先看模型，而是先看用户这一轮要做什么。

任务画像至少包含：

- `kind`：普通对话、最新信息、代码与文件、分析推理、视觉；
- `difficulty`：1 到 3；
- `needsTools`：是否需要工具；
- `needsFreshInfo`：是否必须联网检索；
- `needsImage`：是否要生成图片；
- `needsVision`：是否带图；
- `needsDocs`：是否需要官方 API 文档或价目；
- `tokens`：输入与历史的大致 token；
- `baselineWindow`：用户设置的默认窗口。

例如：

```text
“查一下今天发布的新模型，并比较价格”
→ 最新信息 / 研究
→ 必须联网
→ 需要工具
→ 难度至少 2
→ 还需要官方价目与文档
```

这一阶段不调用模型，只做本地规则判断，所以没有额外费用。

## 2. 第二阶段：硬条件过滤

候选端点先经过不可妥协的条件：

1. 必须启用；
2. 必须具备对话能力；
3. 必须有可用 Key；
4. Auto 模式只接受免费端点，不偷偷切换到付费模型；
5. 上下文窗口必须放得下本轮输入、历史和工具定义；
6. 带图任务要优先有视觉能力的模型。

“免费”的判断不是看名字，而是看供应商的实际单价是否为 `0 / 0`、是否启用、Key 是否就位。

这一步的意义是把“模型答得好不好”与“模型根本没资格回答”分开。

## 3. 第三阶段：候选评分

通过硬条件后，才进入评分。

评分不是单一维度，而是按任务调整权重：

| 因素 | 含义 |
|---|---|
| 任务匹配 | 模型类型与任务类型是否接近 |
| 工具可靠度 | 模型档位、工具调用能力和历史失败 |
| 上下文空间 | 窗口是否足够，剩余空间是否合理 |
| 响应速度 | 本机实测首字延迟 EWMA，不是厂商宣传值 |
| 历史失败 | 连续失败会降权 |
| 视觉加分 | 只有任务确实需要时才有意义 |

近似结构如下：

```text
score =
  taskMatch × taskWeight
  + strength × contextWeight
  + toolAbility × toolWeight
  + speed × speedWeight
  - failurePenalty
```

不同任务的权重会变化：

- 简单闲聊更看速度；
- 研究任务更看工具和上下文；
- 代码任务更看工具与结构能力；
- 难度高的任务降低速度权重；
- 带图任务先把不会看图的模型排除。

速度是次要项，不是唯一标准。一个 1 秒返回但不会调用工具的模型，在需要执行任务的场景里并不算快。

## 4. 延迟来自真实调用

Auto 使用的不是写死的“谁应该更快”，而是本机调用统计：

- 成功调用后更新首字延迟 EWMA；
- 连续失败增加失败计数；
- 下一次路由会降低连续失败端点的分数；
- 切换端点时记录原因。

这使路由会逐渐适应真实网络、供应商限流和本机环境。

同时，速度不能无限压过能力。一个本地小模型可能首批返回很快，但在复杂工具任务里需要更多轮次，最终总耗时和 token 都更高。

## 5. 429 和“请求发出后失败”不是同一种问题

降级链只对尚未产生业务结果的连接级失败更安全。典型的可切换原因包括：

- 地址暂时连不上；
- 请求还没开始生成就返回了错误；
- 端点明显不可用。

如果模型已经流式输出了内容，简单换模型重试可能产生两份计费，也会让用户看到前后不连贯的答案。因此不能用“任何错误都自动重试”掩盖问题。

Auto 的规则应该始终可解释：

```text
为什么选它：能力满足、窗口足够、免费、当前历史延迟较低
为什么换它：连接失败 / 429 / 端点不可达
换了之后是否仍免费：是
```

## 6. 显式模型与 Auto 是两件事

用户明确选择 `deepseek-flash` 时，系统应该尊重这个选择，不能因为任务“看起来更适合 Auto”就换模型。

Auto 只在以下情况生效：

- 用户主动选择“免费模型 Auto”；
- 某个智能体明确绑定 Auto；
- 没有任何显式模型和智能体绑定，系统按默认策略路由。

这条优先级必须固定：

```text
显式指定
  > 智能体绑定
  > 任务类型路由
  > 全局默认
```

否则用户会看到“我明明选了 DeepSeek，实际却用了别的模型”。

## 7. 运行轨迹里应该看到什么

一次 Auto 选择至少应留下：

- 任务分类；
- 难度；
- 是否带图、联网或需要出图；
- 被过滤的候选及原因；
- 最终选中的端点；
- 分数和权重；
- 实际首字延迟；
- 失败后切换的下一站；
- 最终模型的 token 与费用。

这些记录让路由从“黑箱聪明”变成可复现工程。

## 8. 一个可复用的路由顺序

1. **解析任务**：先判断要不要看图、出图、联网、文档或写文件；
2. **硬过滤**：启用、Key、能力、窗口、免费模式；
3. **按任务加权**：不要用一套权重处理所有请求；
4. **使用真实延迟**：厂商宣称只能做先验；
5. **失败可回退但不重复计费**：只对安全的连接级失败降级；
6. **显式选择优先**：用户点名模型时不要自作聪明；
7. **全过程可观测**：为什么选、为什么换都要写进轨迹。

Auto 的目标不是“永远选最强”，而是在任务要求、可靠性、上下文、价格和速度之间给出一个当下最合适的答案。
