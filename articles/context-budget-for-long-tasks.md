# 长任务为什么总断：NexcoreWork 的四区块上下文治理

![NexcoreWork 四区块上下文治理架构图](assets/architecture/context.svg)

> 一句话结论：长任务失败往往不是模型“不够聪明”，而是上下文把工具结果、历史对话、固定规则和当前目标混成一团，最后在关键约束丢失后直接爆窗。

一个简单任务跑了几十步，最后报“上下文超限”，通常已经浪费了大量 token。更糟的是，如果系统为了继续运行简单截断历史，安全规则、用户目标或最新工具结果也会被一起删掉。

NexcoreWork 不把上下文当成一个不断追加的 `messages` 数组，而是拆成四个预算区块，并在超限时按固定顺序治理。

## 1. 四区块不是四种消息角色

四个区块描述的是“上下文中的不同职责”：

| 区块 | 内容 | 关键属性 |
|---|---|---|
| 固定前缀 | 身份、角色、安全规则、工具与技能方法 | 本轮相对稳定，适合缓存 |
| 注入层 | 项目记忆、召回记忆、知识片段、文件清单、任务画布 | 高价值，可重建或压缩 |
| 会话历史 | 用户与助手的历史消息、工具结果 | 可压缩，但不能修改原记录 |
| 当前输入 | 这一轮用户真正发送的目标和附件说明 | 最重要，不能截断后假装完整 |

如果只看总 token，很容易把四类内容都当成可随意删减的文本。实际上，它们的价值完全不同。

例如，最近一次工具返回的语法错误比十条早期闲聊更重要；一条安全约束丢失，可能比上下文少 5,000 token 严重得多。

## 2. 超限时的固定顺序

治理顺序必须固定，否则同一份会话每轮都可能得到不同结果，问题无法复现。

NexcoreWork 的降级阶梯是：

```text
1. 清理旧工具结果
2. 结构化压缩会话历史
3. 缩减注入层
4. 仍然超限才拒绝执行
```

每一步都能在轨迹里留下事件，并记录释放了多少 token。

### 第一步：清理工具结果

工具结果经常是上下文中体积最大、性价比较低的部分。旧的文件列表、网页正文和日志可以替换为短预览，再保留回执引用。

做法不是直接删掉调用关系，而是：

- 最近几次工具结果保持原样；
- 更早的结果换成截断预览；
- 保留回执 ID 和读取方法；
- 需要原文时再按下钻引用取回。

这样模型仍然知道“自己做过什么”，但不需要每轮搬一整份日志。

### 第二步：结构化压缩

简单摘要会丢细节。更稳的方式是生成结构化保留项，例如：

- 用户目标；
- 已确认约束；
- 已完成事项；
- 未完成事项；
- 最近失败原因；
- 关键文件路径；
- 可回读的回执引用。

压缩后仍然要检查摘要是否保留住必须信息。NexcoreWork 会做探针核对，不达标就不把压缩结果当成成功。

### 第三步：缩减注入层

当工具结果和会话压缩仍然不够，才削注入层。优先级大致是：

- 先去掉可重新获取的知识片段；
- 再去掉较旧的记忆；
- 保留项目目标、当前任务画布和安全约束。

固定前缀中的身份、安全规则和关键工具方法不能为了腾空间而静默消失。

### 第四步：拒绝，并说清怎么继续

如果做完前三步仍然超限，继续硬塞只会产生不可预测的模型输出。此时应拒绝本轮执行，并告诉用户：

- 当前窗口多大；
- 超了多少；
- 已经做了哪些清理；
- 可以调高窗口、拆分任务或换成大窗口模型；
- 原文仍然保存在哪里。

“拒绝”不是失败体验，假装成功才是。

## 3. 为什么不能只保留最后 N 条消息

最常见的错误实现是：

```ts
messages = messages.slice(-20);
```

它有三个问题：

1. 固定条数不等于固定 token；
2. 长工具结果可能一条就顶满窗口；
3. 最早写入的用户约束会被最先删掉。

一个项目做到第 30 步时，最初那句“不要修改现有配色”很可能比对上一句“继续”更重要。

因此历史截断必须和结构化保留层一起做。最近原文保证接续，压缩摘要保证目标不丢，回执保证事实可查。

## 4. 原始记录与模型上下文分离

上下文治理不是数据库清理。

从模型请求里移出去的内容，仍然应保存在本机：

- 原始会话消息；
- 工具参数与回执；
- 压缩前快照；
- 每次压缩的版本；
- 可回读引用。

用户回看历史时应该能看到完整记录，模型则只在预算内读取必要部分。这两件事分开之后，压缩才能既省 token 又不销毁证据。

## 5. 任务画布为什么也属于上下文

长时间执行后，模型容易忘记“现在走到哪一步”。只靠聊天历史很难恢复流程结构。

NexcoreWork 会把已完成步骤、工具调用、文件变化和回执整理成一张可折叠的任务画布。长流程中的每个节点都能回到当时的原始工具结果。

它的作用是：

- 给模型一个当前状态；
- 给用户一个可读的进度图；
- 给压缩提供一个结构化骨架；
- 给失败恢复提供断点。

画布不是装饰图，而是上下文治理后的“高层状态”。

## 6. 一次预算快照

项目基准测试里曾记录过一组 32K 窗口附近的四区块占比：

| 区块 | 约 token |
|---|---:|
| 固定前缀 | 5,053 |
| 注入层 | 5,411 |
| 会话历史 | 14,685 |
| 当前输入 | 817 |

合计约占窗口的 79.2%。这组数字的意义不是证明某个固定比例最好，而是说明：如果不做区块预算，单个区块就可能把整个窗口吃掉。

对用户更重要的是，设置和运行面板能看到：

- 当前估算 token；
- 窗口大小；
- 是否发生清理或压缩；
- 压缩前后的版本；
- 本轮实际调用的模型窗口。

## 7. 上下文治理的可复用原则

1. **先分职责，再算总 token**：固定规则、动态资料、历史和当前任务不能混算；
2. **先清理可恢复内容**：工具结果和日志优先变成预览；
3. **摘要必须结构化**：目标、约束、进度、失败、路径都要保留；
4. **原文永不因压缩而删除**：只是从请求中移出；
5. **每次治理都留事件**：否则无法解释模型为什么突然改变；
6. **安全约束最后丢**：宁可停止，也不能悄悄失去边界；
7. **拒绝时给出可执行恢复方案**：调窗口、拆任务或换模型。

长任务的关键不是让模型“记得更多”，而是让系统知道什么必须记得、什么可以重建、什么应该按需读取。
