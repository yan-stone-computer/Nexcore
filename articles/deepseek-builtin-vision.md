# DeepSeek 当主脑，内置视觉当眼睛：文本模型怎样真正看懂截图

> 一句话结论：多模态能力不一定要求主模型自己会看图。更稳妥的工程结构是，让 DeepSeek 这类文本模型负责理解任务、规划步骤和调用工具，让内置视觉模型负责提供可复核的画面事实，再把文字证据交回主模型。

大模型应用里有一个很常见的误区：只要任务涉及图片，就把整轮对话切到一个“会看图”的模型上。这个做法看起来直接，实际会同时破坏三件事：

- 用户明确选择的 DeepSeek 可能根本没有参与任务；
- 识图模型擅长描述画面，却不一定擅长规划、写代码和调用工具；
- 一整轮对话为了看一张图换了模型，后续回答的风格、上下文和成本都会突然变化。

NexcoreWork 采用的不是“换主模型”，而是“分工”。

## 1. 主模型和视觉模型各做什么

| 角色 | 负责 | 不负责 |
|---|---|---|
| DeepSeek 主模型 | 理解目标、拆步骤、选择工具、修改文件、组织最终回答 | 凭空描述自己没看过的像素 |
| 内置视觉模型 | 读取图片、截图、渲染帧，给出画面事实和不确定项 | 决定整个工程怎么做 |
| 渲染工具 | 把 HTML、SVG 或页面变成可检查的 PNG | 判断画面是否好看 |
| 质检技能 | 约束“先看、再做、再复核”的顺序 | 假装识图成功 |

这条分工与任务路由器一致：带图不等于把主对话模型换掉。只要当前主模型不会看图，就先把图片交给视觉端点，读成一段带边界的文字，再把这段文字注入主模型上下文。

## 2. 一次带图任务的真实链路

```text
用户消息 + 图片/截图路径
        │
        ├─ 主模型会看图？
        │     ├─ 是：图片可作为当前轮输入
        │     └─ 否：调用内置视觉端点读图
        │
        ├─ 视觉结果以“图片内容”注入上下文
        │
        ├─ DeepSeek 根据文字证据决定是否调用工具
        │
        ├─ 渲染预览 → 内置识图 → 修正
        │
        └─ 输出结论；没有证据就明确说没有
```

这里有两个入口，解决的问题不同：

- `builtin_view_image`：读取**当前消息附带的图片**，适合理解用户刚上传的截图。
- `builtin_inspect_image`：读取**工作区里的图片文件**，适合检查渲染出的 SVG、HTML 页面、图表和动画帧。

两者最终都会调用设置里的视觉端点，但工作区文件与当前附件不是同一类对象。把入口分开，才能让权限、路径和上下文边界都保持清楚。

## 3. 为什么一张图一次调用

多张图塞进一个请求看起来很省钱，工程上却很难控制结果。很多兼容端点只会认真处理第一张图，剩下的图片被忽略；返回一段笼统描述后，又很难知道哪句话对应哪一张。

NexcoreWork 的做法是：

1. 一张图发一次视觉请求；
2. 多张图并行，最多 4 路；
3. 每张答案按“【图 N】”分列；
4. 调用次数、视觉 token 和费用照常记账；
5. 单张失败不影响其他图片，但最终必须说明哪一张没有看到。

伪代码可以压缩成这样：

```ts
const workers = Array.from(
  { length: Math.min(images.length, 4) },
  () => worker()
);

await Promise.all(workers);
```

这样做的代价是请求数增加，但收益是证据边界清楚。视觉检查不是“发过去就算看过”，而是每一张都有独立的结果。

## 4. 让视觉任务自动带上质检技能

工具存在，不代表模型一定会调用。真实运行里，模型经常直接写完文件就回答“已完成”。

因此视觉质检被做成内置技能，并在检测到网页、界面、截图、动画、SVG、图片、图表等任务时自动加入会话。规范要求：

1. 用户带参考图时，先问清主体、层级、尺寸和明显问题；
2. 修改现有页面时，先读 HTML、CSS 和相关资源；
3. 写完后调用 `builtin_render_preview`；
4. 对真实渲染结果调用 `builtin_inspect_image`；
5. 按裁切、比例、遮挡、层级、对齐、文字可读性逐项修正；
6. 没有新的截图证据，不得声称做过视觉验证。

技能不是一段“让模型更聪明”的咒语，而是把顺序写死：先看目标，再做最小改动，最后看真实产物。

## 5. 一次 DeepSeek + 内置视觉的真实运行

实测任务是用官网首屏截图做只读质检，主模型明确选择 `deepseek-flash`，不调用外部识图，也不执行命令。

运行记录：

| 项目 | 结果 |
|---|---|
| 主模型 | `deepseek-flash` |
| 工具 | `builtin_inspect_image` |
| 调用次数 | 1 次 |
| 识图耗时 | 约 6.0 秒 |
| 运行状态 | 完成 |
| 文件修改 | 无 |

DeepSeek 收到的不是 base64 图片，而是视觉端点返回的文字事实，例如：

- 导航栏、主标题、按钮组和产品演示图是否完整；
- 是否存在遮挡、错位或比例失真；
- 哪些细节因像素不足无法稳定识别；
- 哪些结论只是模型推断，不能当作已确认缺陷。

最终回答同时保留了正向证据和未核验项。这比一句“看起来没问题”更有价值，因为读者知道结论从哪里来。

## 6. 视觉失败也应该可解释

视觉端点可能超时、限流或返回 429。此时系统不能做两件事：

- 不能把旧截图或上一轮结论冒充成本轮结果；
- 不能因为主模型很会写，就把“没看到”说成“已完成检查”。

正确行为是明确说明：

```text
本轮没有拿到可信的视觉返回。
可以确认文件存在、尺寸有效，但不能确认画面内容完整。
需要换视觉端点、等待限流恢复，或重新提供可访问的图片。
```

这类失败信息同样应写入运行轨迹。视觉模型的 429 不是主模型的错，也不能被主模型用自然语言掩盖。

## 7. 可复用的设计原则

文本模型接入视觉能力时，可以按以下顺序落地：

1. **先拆能力，再选模型**：对话、视觉、出图、语音分别声明能力；
2. **主模型不因带图被偷偷替换**：视觉模型只提供证据；
3. **附件图片和工作区图片分开**：权限与入口不能混用；
4. **一张图一次调用**：准确、可追踪、可局部重试；
5. **视觉结论必须带证据边界**：成功、失败、低置信度都要写清；
6. **用技能约束流程**：不是所有模型都会自觉执行“渲染后再检查”；
7. **最后期限由证据决定**：视觉端点没返回，任务就不能标记为视觉已验证。

DeepSeek 负责“想清楚和控制工具”，视觉模型负责“看见并说出事实”。这两件事分开之后，文本模型的可用范围反而变大了，系统也更容易解释每一次判断到底基于什么。
