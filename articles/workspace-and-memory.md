# 为什么本地优先智能体需要工作区和项目记忆

> 一句话结论：聊天框只能承载一次问答，真正能持续工作的智能体必须有明确的工作目录、可恢复的项目记忆和不会越界的本地数据层。

![NexcoreWork 项目记忆架构图](assets/architecture/memory.svg)

如果把 Agent 当成“更长的聊天框”，项目很快就会变成一堆无法归档的内容：

- 这次生成的页面在哪个目录？
- 上次说的设计约束还存在吗？
- 继续修改时，模型能否看到之前做过的文件变化？
- 删除对话会不会误删整个项目？
- API Key、对话记录和工作区文件分别存在哪里？

NexcoreWork 用两个基础对象回答这些问题：**工作区**和**项目记忆**。

## 1. 新对话先选工作区

每次新建对话时可以指定一个真实文件夹。工作区不是 UI 上的标签，而是工具权限的根：

- 文件读写必须落在工作区内；
- 命令的工作目录固定在工作区内；
- 项目记忆写入这个工作区；
- 后续轮次默认沿用同一个目录；
- 换项目时切工作区，不把两个项目的上下文混在一起。

创建会话时就会校验路径是否存在、是否为目录、是否不是危险根目录，而不是等模型第一次写文件才报错。

```text
选择工作区
    ↓
校验目录
    ↓
记录在会话上
    ↓
本轮与后续运行复用
```

这解决的是“文件到底写到了哪里”这个最基础、也最容易在 Agent 产品里变模糊的问题。

## 2. 项目记忆先写请求，再执行

很多记忆系统只保存最后的对话摘要。这样一旦进程中途退出，用户这轮到底要求了什么就丢了。

NexcoreWork 的顺序是：

1. 运行开始；
2. 先把本轮请求写入项目记忆；
3. 再加载上下文、调用模型和执行工具；
4. 完成后补写结果和交付物。

即使模型在第 30 步崩溃，工作区里仍然知道：

- 用户什么时候提出了什么；
- 这一轮想完成什么目标；
- 使用哪个工作区；
- 之后有没有结果。

项目记忆不是替代原始日志，而是给下一次继续工作提供一个稳定的项目级入口。

## 3. `.NexcoreWork` 记录什么

工作区里的 `.NexcoreWork/` 目录用于承载项目级上下文，例如：

```text
project/
├─ src/
├─ website/
├─ outputs/
└─ .NexcoreWork/
   ├─ memory.md
   └─ ...
```

它记录的是项目约定、已完成事项、关键决策和续接信息，而不是把整个数据库复制一份。

好的项目记忆应回答：

- 这个项目是什么；
- 用户有哪些稳定约束；
- 哪些路径和接口已经确定；
- 已完成什么；
- 当前还有哪些未解决项。

不该记录：

- 每一段工具输出原文；
- 可以重新读取的整份源码；
- API Key、密码、私钥；
- 用户没有确认的猜测。

## 4. 三层长期记忆与项目记忆是不同层级

NexcoreWork 的长期记忆分为：

| 层级 | 内容 | 注入方式 |
|---|---|---|
| L1 | 原子事实与偏好 | 按当前任务关键词召回，最多若干条 |
| L2 | 场景经验与方法 | 相关时注入 |
| L3 | 稳定画像与核心规范 | 固定高优先级注入 |

项目记忆解决“这个文件夹里的项目做到哪”，长期记忆解决“用户长期偏好什么、以前总结过什么方法”。

两者不能混在一起。否则换到另一个项目时，上一个项目的具体状态会被误当成全局事实。

## 5. 五分钟后压缩，而不是每五分钟乱跑

对话结束后，系统可以在空闲达到阈值时触发记忆提炼。默认阈值可配置，例如 5 分钟；设为 0 则关闭。

触发条件不是“手机上的定时器一到就提炼”，而是：

- 这个会话上次提炼后出现了新的已完成对话；
- 会话已经空闲达到阈值；
- 当前没有新的运行正在使用同一会话。

提炼内容只取用户输入和助手最终回复，不把整段工具日志全部送去模型。这样做的原因是：

- 成本更低；
- 噪声更少；
- 工具输出原文已经存在于运行记录；
- 项目结论比原始日志更适合长期保留。

## 6. 去重、替代与敏感信息过滤

记忆最容易变成垃圾堆的地方不是写入，而是重复写入。

写入管线至少应做：

1. 清洗代码块和过长文本；
2. 归一化措辞；
3. 查找同主题旧记录；
4. 新事实取代旧版本，旧版本进历史而不是直接消失；
5. 知识库已经收录的事实不重复写成个人记忆；
6. 命中密码、私钥、手机号、邮箱等内容整条拒绝；
7. 超过容量时按使用频率和新旧淘汰，淘汰记录进入回收区。

“记得多”不等于“记得好”。一个会持续注入错误旧偏好的记忆系统，比没有记忆更危险。

## 7. 本地数据边界

本地优先包含三层含义：

### 数据在本机

- SQLite 保存会话、记忆、工具回执和设置；
- 工作区保存项目文件；
- API Key 保存在本机 `.env`；
- 导出备份不包含密钥。

### 网络默认受限

- 服务只监听 `127.0.0.1`；
- 云端模型和联网工具需要显式授权；
- 本地模型可以不出网；
- 跨站请求要校验 Host、Origin 和请求来源。

### 写入有边界

- 文件路径必须在工作区内；
- 隐藏凭据和符号链接逃逸要拒绝；
- 高风险写入和命令执行需要审批；
- 修改现有文件要保留差异回执；
- 删除对话是否删除工作区必须是用户明确选择。

需要说清楚的是：这是文件能力边界，不是操作系统级沙箱。它不是虚拟机，也不能把一条被批准的本机命令变成安全命令。

## 8. 什么情况下应该选哪个工作区

一个实用原则：

> 一个需要持续维护、共享文件和项目记忆的任务，对应一个工作区。

例如：

- 官网源码和素材放一个工作区；
- 安装包与发布脚本放同一个发布项目；
- 临时问答可以用默认工作区；
- 不相关的两个产品不要为了省事共用一个目录。

这样删除对话、切换模型、继续任务和导出文件都不会互相牵连。

## 9. 可复用的设计清单

- 新对话可以选择真实文件夹；
- 路径在创建时就校验，不等到工具执行；
- 会话记住工作区，下一轮继续使用；
- 每轮先写项目记忆，再执行；
- 完成后补结果，不覆盖请求原文；
- 长期记忆分层，不和项目状态混用；
- 空闲压缩只在对话结束且确实满足条件时触发；
- 敏感信息在进入长期记忆前拦截；
- 原始对话、工具回执和数据库不因压缩而删除；
- 删除对话与删除工作区必须是两个清楚的动作；
- 服务只监听本机，云端能力显式授权；
- 不把应用级路径检查描述成操作系统级沙箱。

工作区让 Agent 有“在哪里工作”的边界，项目记忆让它知道“已经做到哪”，长期记忆让它理解“和谁一起工作”。三者分开，连续项目才不会变成一堆互相污染的上下文。
